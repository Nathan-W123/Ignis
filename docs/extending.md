# Extending Ignis

Every extension below is a real edit to a real place. The repository is
layered so that adding physics does not mean touching everything.

Before starting: `./scripts/build.sh && ./scripts/test.sh`. If the suite is
green before your change and red after it, the test that went red tells you
what you broke.

---

## Add a chemical species

**Data only — no code.**

The species database is `data/thermo/ignis_nasa7.yaml`, generated by
`tools/build_thermo_db.py` from Cantera's `nasa_gas.yaml` and `gri30.yaml`.
Each entry carries the two NASA-7 coefficient sets, the temperature ranges,
the elemental composition and the Lennard-Jones transport parameters, plus the
SHA-256 of the source file it came from.

To add a species that exists in those sources, add its name to the list in
`tools/build_thermo_db.py` and re-run it. To add one that does not, append an
entry by hand in the same format — the loader validates the element map
against the molar mass, so a typo in the composition is caught immediately.

Species are then selected per run by element set (`species.elements`) or
explicitly (`species.include`). A new species with an element no propellant
contains costs nothing; the element matrix simply has a zero row.

> The YAML loader disables PyYAML's bool and null resolvers. Without that, the
> species `NO` parses as the boolean `False` and `NO2`/`N2O` do not — a
> genuinely confusing bug worth knowing about before editing the generator.

## Add a propellant

**Data only.** Append an entry to `data/propellants/ignis_propellants.yaml`
in the same shape as the shipped ones — elemental composition, molar mass,
absolute reference enthalpy with its temperature, density, liquid
c<sub>p</sub>, phase, and a `source:` line naming where each number came from.
Copy a shipped cryogen as the template; do not copy the numbers.

The enthalpy must be **absolute** — formation enthalpy included — and stated at
the temperature the propellant is actually delivered at. That is what makes the
chamber solve a genuine constant-enthalpy problem from the tank rather than
from gaseous reactants at 298.15 K. For the cryogens shipped here the values
are the NASA CEA library's liquid enthalpies at the normal boiling point, cited
in the file.

Then make sure the product species for the new elements exist in the thermo
database, and set `species.elements` accordingly.

## Add a wall material or a coolant

**Materials** live in `data/materials/ignis_materials.yaml` as a linear k(T)
fit with its validity range and a citation. `WallMaterial` reports
extrapolation by name rather than silently continuing, so give the range
honestly.

**Coolants** are tabulated CSVs under `data/coolants/`, generated by
`tools/build_coolant_tables.py` from CoolProp's reference equations of state.
To add one, add its name to the fluid list in that script and re-run it. The
axis spacing is deliberately non-uniform (2 K below 1.5·T<sub>c</sub>, 8 K to
2.5·T<sub>c</sub>, 25 K above) because the near-critical region is where the
interpolation error lives; `tests/unit/test_thermal.cpp` measures that error
against CoolProp at points between nodes, so a badly chosen grid fails the
suite rather than quietly degrading.

## Add a configuration key

1. Add the field to the right struct in `include/ignis/io/Config.hpp`.
2. Parse it in `src/io/Config.cpp`, using `ConfigNode::number(lo, hi, default)`
   so the range check and the error message come for free.
3. Add the key to the allowed-key list for its section (unknown keys are
   rejected, which is what catches typos).
4. If a study should be able to drive it, register it in
   `src/optimize/Parameters.cpp` — one line in `paramTable()` with its units
   and a setter/getter pair.
5. Document it in [`configuration.md`](configuration.md) and add a line to a
   shipped config if it is meaningful there.

`tests/unit/test_io.cpp` loads **every** shipped configuration and checks the
parameter registry round-trips, so steps 3 and 4 are enforced.

## Add an output metric

One entry in `metricTable()` in `src/optimize/Parameters.cpp`:

```cpp
{"cooling.min_fin_efficiency",
 {"-", [](const SteadyEngineResult& r) { return r.cooling.min_fin_efficiency; }}},
```

(`min_fin_efficiency` is an illustration, not an existing field — you would add
it to `CoolingResult` first.)

It is immediately available as a sweep metric, an optimisation objective or
constraint, and a Monte Carlo output. Add it to
[`configuration.md`](configuration.md)'s metric list.

## Add a nozzle contour type

`NozzleGeometry` builds the wall from analytic segments in
`src/nozzle/NozzleGeometry.cpp`. Each segment is a straight line or a circular
arc with C¹ joins; the constructor validates continuity and monotonicity and
`tests/unit/test_nozzle.cpp` checks the maximum radius and slope jumps.

To add, say, an MOC contour: add a `DivergentType` enum value, a branch in the
segment builder that emits either a new segment kind or a dense sampled
polyline, and keep the same validation. Nothing downstream needs to change —
`NozzleFlow` only ever asks the geometry for `radius(x)` and `area(x)`.

## Add a heat-transfer correlation

`src/thermal/HeatTransfer.cpp` holds the gas-side model and
`src/thermal/RegenerativeCooling.cpp` the coolant-side Nusselt selection
(`nusselt_correlation: dittus-boelter | gnielinski`). Adding a third is a new
enum value, a new branch and a new test.

**Please also add an uncertainty knob.** Every empirical correlation in Ignis
has a multiplier (`bartz_multiplier`, `nusselt_multiplier`) whose whole purpose
is to let the Monte Carlo campaign carry the correlation's own uncertainty.
A correlation without one implicitly claims to be exact.

## Add a distribution

`src/uncertainty/MonteCarlo.cpp`. Implement `draw()` for the new kind and add
it to the parser. Two rules:

* Draw from the sample's **own** RNG, seeded `SplitMix64(seed, index)` — never
  from a shared generator, or thread-count independence breaks and
  `run_all.sh`'s `cmp` check will catch you.
* Truncation is applied by redrawing, not by clamping. Clamping piles mass on
  the bounds and quietly changes the distribution.

## Add a solver mode

The equilibrium solver exposes `tp`, `hp`, `sp` and `uv`. A new problem type
(say constant-entropy, constant-volume) means a new entry point that sets up
the same Newton system with a different last row. `buildReduced()` is the
shared machinery; the state-specific part is small and localised.

Whatever you add, add the matching **residual**: every solve reports how well
it satisfied its own specification, and that is what the tests check.

## Add a figure

`python/ignis_viz/figures.py`, then register the job in
`python/make_figures.py`. Read data through `ignis_viz.data.read_table`, which
understands the `# units:` header line Ignis writes and gives you
`t.label(column, fallback)` for axis labels.

Use `ignis_viz.style`: the palette is validated (worst adjacent
colour-vision separation 9.1 in OKLab ΔE×100, worst adjacent normal-vision
separation 19.6), and colour is assigned by job — categorical for identity,
one-hue sequential for magnitude, blue/red-with-grey-midpoint for polarity.
Never a second y-axis; use a second panel.

## Things to preserve

These are not style preferences; they are what makes the results trustworthy.

1. **Never silently clamp a failed solve into a valid-looking state.** Throw
   the right exception with an actionable message. A sweep that reports
   `169 points, 52 failed` is telling the truth; one that reports 169 successes
   by clamping is not.
2. **Report residuals, don't assume them.** Every solve recomputes how well it
   satisfied its own equations and carries that number out to the caller.
3. **Keep ideal and corrected quantities separate.** `c_star_ideal` and
   `c_star`, `isp_ideal` and `isp`, `thrust_ideal` and `thrust`. An empirical
   efficiency must always be visible as an empirical efficiency.
4. **Label every empirical correlation**, in the code, in the report and in
   [`theory.md`](theory.md), with its source and its scatter.
5. **Cite data.** Every number in `data/` has a source in the file next to it.
6. **Keep the study layer running the same code path as a single run.** The
   test `a sweep reproduces the single-point analysis exactly` compares them
   bit-for-bit; there must never be a fast approximate model that can disagree
   with the real one.
7. **Keep Monte Carlo thread-count independent.** It costs nothing and it means
   a result can be reproduced on a different machine.
